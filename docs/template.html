01

진짜 어려운 부분은 어디인가

공공 API에서 버스 위치를 받아 화면에 뿌리는 일은 스크립트 백 줄이면 됩니다. 어려운 건 외부 시스템의 실패와 데이터 유실을 사용자가 눈치채기 전에 어떻게 관측하고 격리할지를 정하는 것입니다.

이 프로젝트에서 실제로 시간을 쓴 지점은 세 가지였고, 셋 다 외부에 의존하는 시스템이 조용히 망가지는 방식에 관한 것이었습니다.

CONSTRAINT

하루 1,000회

개발계정 한도입니다. 노선 정류장 목록을 요청마다 부르면 몇 분 만에 소진됩니다. 무엇을 미리 받고 무엇을 그때 받을지가 설계의 출발점이 됐습니다.

TRUST

200인데 실패

이 API는 정상 응답으로 내려주면서 본문 헤더에 오류 코드를 담습니다. 필드명은 공개 문서에 없고 활용가이드에만 있습니다. 믿을 수 없는 응답을 전제로 클라이언트를 짜야 했습니다.

LOSS

조용한 유실

로그는 안 와도 에러가 안 납니다. 브라우저가 이탈 시점의 fetch를 폐기하고, 배치 한 건이 불량이면 나머지가 같이 버려집니다. 사라지는 걸 세는 장치가 필요했습니다.

그래서 이 문서는 기능 목록이 아니라 이 세 가지에 어떻게 대응했는지를 코드로 따라갑니다.

02

파일을 나눈 기준은 "기능"이 아니라 무엇이 무엇을 알아도 되는가입니다. 화면은 데이터가 어디서 오는지 몰라야 하고, 저장 계층은 HTTP를 몰라야 합니다. 그래야 한쪽을 바꿔도 다른 쪽이 안 깨집니다.

03

서버를 두는 건 선택이 아니다

"정적 페이지 하나로 만들면 안 되나"는 자연스러운 질문입니다. 브라우저에서 공공 API를 직접 부를 수 없는 이유가 세 가지 겹쳐 있습니다.

이유무슨 일이 생기나
인증키 노출클라이언트 코드에 키를 넣으면 개발자 도구를 연 누구나 가져갑니다. 내 하루 1,000회를 남이 씁니다.
CORS공공 API에 Access-Control-Allow-Origin이 없어 브라우저가 응답을 버립니다.
혼합 콘텐츠API가 http://ws.bus.go.kr입니다. https 페이지에서 http 요청은 차단됩니다.

그래서 키는 서버 프로세스의 환경변수로만 읽고 브라우저로 한 글자도 내려보내지 않습니다. .env는 .gitignore에 있고, 저장소에는 .env.example만 들어갑니다.

실무에서 자주 막히는 지점 인증키가 Encoding / Decoding 두 종류로 발급됩니다. HTTP 클라이언트가 쿼리스트링을 인코딩할 때 이미 인코딩된 키를 한 번 더 인코딩하면 키가 깨집니다. 어느 쪽이 맞는지는 라이브러리마다 달라서, .env.example에 "둘 다 시도해보라"고 적어 뒀습니다.
04

외부 API를 믿지 않는 법

이 클라이언트는 응답이 정상일 거라고 가정하지 않습니다. 네 가지를 각각 방어합니다.

① 엔드포인트를 한 표에 모은다

왜. 응답 필드명과 오퍼레이션 철자가 공개 웹페이지에 없고 각 서비스의 활용가이드 문서에만 있습니다. 실제 문서와 다를 가능성이 있으니, 고칠 곳을 코드 전체에 흩어놓지 않고 이 표 하나로 모았습니다. getStaionByRoute의 오타처럼 보이는 철자도 원문 그대로 둡니다 — 우리가 고칠 대상이 아닙니다.

② HTTP 200이어도 실패일 수 있다

왜. raise_for_status()만 보면 실패를 놓칩니다. 이 API는 200으로 내려주면서 본문의 headerCd에 오류를 담기 때문입니다. 그래서 본문을 파싱한 뒤 코드를 확인합니다.

재시도도 종류를 나눴습니다. 초당 호출 제한(코드 23)은 잠깐 쉬면 풀리므로 재시도할 가치가 있지만, 잘못된 파라미터는 백 번 보내도 같은 결과라 바로 예외로 올립니다. 네트워크 오류는 지수 백오프(0.5s → 1.0s)로 최대 3회입니다. 타임아웃은 처음부터 넣었습니다 — 없으면 외부가 느려질 때 워커가 묶여 연쇄 장애가 납니다.
왜. 헤더 키가 msgHeader일 수도 comMsgHeader일 수도 있어 둘 다 받습니다. 오퍼레이션마다 래핑이 조금씩 달라서, 여기서 흡수하지 않으면 호출부마다 분기가 생깁니다.

③ 항목이 하나면 리스트가 아니다

왜. XML을 dict로 바꾸면 항목이 1개일 때 dict, 여러 개일 때 list로 옵니다. 이걸 흡수하지 않으면 "버스가 한 대만 운행 중일 때만 터지는 버그"가 생기는데, 이런 건 새벽에나 재현됩니다. 테스트로도 고정해 뒀습니다.

④ 필드명이 틀려도 조용히 죽지 않는다

왜. 활용가이드를 받기 전까지 정확한 철자를 확신할 수 없었습니다. 후보를 여러 개 받아 먼저 있는 것을 쓰되, 끝까지 못 찾으면 경고 로그를 남깁니다. 그냥 row.get("busRouteNm")으로 썼다면 필드명이 다를 때 None이 조용히 채워지고, 화면에는 빈칸이 뜨고, 원인은 한참 뒤에 찾게 됩니다. 틀렸다는 사실이 즉시 드러나는 게 핵심입니다.
왜 정규화 계층을 따로 뒀나. 외부 스펙이 앱 안쪽으로 새어 들어오지 않게 하는 방어막입니다. stopFlag가 문자열 "1"인 것, 혼잡도가 숫자 코드인 것, 오타처럼 보이는 congetion까지 전부 여기서 끝납니다. 화면과 저장 계층은 stopped: True와 congestion: "혼잡"만 봅니다. 나중에 필드명이 바뀌면 이 함수 하나만 고치면 됩니다.
05

데이터를 성격으로 나눈다

이 프로젝트의 핵심 설계 판단입니다. 하루 1,000회라는 제약이 구조를 결정했습니다.

모든 데이터를 똑같이 다루면 안 됩니다. 노선의 정류장 순서는 몇 달에 한 번 바뀌고, 버스 위치는 30초마다 바뀝니다. 바뀌는 속도로 갈랐습니다.

데이터언제 받나어디에호출
정적노선 목록 · 노선별 정류장 순서 · 정류장 마스터하루 1회 배치 (또는 최초 조회 시)SQLite노선당 2회
동적버스 위치 · 도착 예정사용자 요청 시메모리 TTL 20초요청당 1회

노선 20개를 미리 적재하면 초기 호출이 최대 40회, 하루 1,000회 한도의 4%입니다. 이 숫자는 실제 사용량이 아니라 사전 적재 비용의 상한입니다 — 이후 사용자 요청에 따른 on-demand 호출이 여기에 더해지므로, 한도는 계측으로 관찰합니다(14장).

스키마 — 재적재해도 늘지 않게

왜 (route_id, seq)가 기본 키인가. 배치를 하루에 두 번 돌리거나 실패해서 다시 돌려도 정적 데이터의 행이 늘어나면 안 되기 때문입니다. 자동 증가 ID를 쓰면 같은 정류장이 두 번 쌓입니다. 자연 키를 기본 키로 잡고 upsert 하면 정적 적재가 그 자체로 멱등해집니다.

주의할 것은 이 멱등성이 정적 마스터 데이터에만 해당한다는 점입니다. 행동 로그의 event_id 는 현재 raw JSONL 단계에서 중복 제거에 쓰이지 않고, 후속 적재가 dedup 키로 쓸 수 있도록 보존만 합니다.
왜 stations에도 같이 넣나. 노선의 정류장 목록을 받으면 정류장 마스터도 공짜로 따라옵니다. 이걸 버리고 나중에 정류장 검색용으로 또 받으면 호출을 두 번 쓰는 셈입니다. 한 번 받은 데이터에서 뽑아낼 수 있는 건 전부 뽑아 둡니다.

API를 부르지 않고 만드는 데이터

왜. "이 정류장을 지나는 노선"은 전용 API(getRouteByStation)가 있지만 부르지 않습니다. 노선별 정류장 목록을 이미 받아뒀으니 관계를 뒤집으면 나오기 때문입니다. 그래서 route_stations에 ars 인덱스를 걸어 뒀습니다.

대신 사전 적재한 노선 범위 안에서만 완전하다는 한계가 생기는데, 이걸 숨기지 않고 응답에 coverage_note로 함께 담아 화면에 표시합니다. 불완전한 데이터를 완전한 것처럼 보여주는 게 제일 나쁩니다.

새로고침 연타를 막는 20줄

왜 나이(age)를 같이 돌려주나. 캐시 히트일 때 "몇 초 전 데이터인지"를 알아야 화면에 "32초 전"을 표시할 수 있기 때문입니다. 값만 돌려주면 그 정보가 사라집니다.

이 캐시는 성능보다 외부 호출량과 초당 제한(코드 23)을 완화하는 것이 목적입니다. 같은 워커에서 짧은 시간 안에 같은 조회가 반복되면 외부 호출이 한 번으로 줄어듭니다. 다만 캐시는 프로세스 안에만 있으므로 이것만으로 전역 한도가 보장되지는 않습니다 — 한도는 api_usage 로 따로 관측합니다.
왜 관측 정보를 같이 반환하나. 이 함수는 데이터와 함께 latency_ms, cache, data_age_sec, status를 돌려줍니다. 이 값이 그대로 화면 오른쪽 로그 패널의 api.call 이벤트가 됩니다. 관측을 나중에 덧붙이면 호출부마다 시간 재는 코드를 넣게 되는데, 반환값에 포함시키면 한 번만 재고 끝입니다.

실패해도 예외를 밖으로 던지지 않고 빈 리스트 + status 502로 돌려줍니다. 버스 위치를 못 받았다고 노선도 전체가 안 보이면 안 되기 때문입니다.
06

버스 번호로 찾기 — 가장 많이 고친 곳

처음에 틀렸던 것 첫 구현은 검색을 "노선번호"라고 부르고 캐시에서만 찾았습니다. 두 가지가 잘못됐습니다. 사용자가 아는 것은 버스에 적힌 4312이지 내부 ID 104900034가 아니고, 캐시에만 의존하면 사전 적재하지 않은 402번을 탄 사람이 "없는 버스"라는 답을 받습니다.

용어는 전부 "버스 번호"로 바꾸고 노선 ID는 화면에서 없앴습니다(로그의 route_id로만 남습니다). 구조는 캐시 우선 · 실시간 폴백 · 결과를 캐시에 채움으로 바꿨습니다.

왜 "정확히 일치"를 조건에 넣었나. 캐시에 무언가 있다고 바로 끝내면 안 됩니다. 4를 쳤는데 캐시에 4312만 있고 402가 아직 없으면 402를 영영 못 찾습니다. 그래서 정확히 일치하는 번호가 있을 때만 캐시에서 끝내고, 부분 일치뿐이면 실시간으로 한 번 더 확인해 합칩니다.

그리고 외부 조회가 실패해도 캐시에 있던 부분 일치 결과는 돌려줍니다(source: "cache_only"). 외부가 죽었다고 사용자를 빈손으로 보내지 않습니다.
왜. 서울에는 152와 1522가 둘 다 있습니다 — 152를 친 사람에게 1522를 먼저 보여주면 안 됩니다. 튜플 정렬로 정확히 일치 → 접두 일치 → 짧은 번호 → 사전순을 한 줄에 담았습니다. 문자열 비교라서 마을버스 강남06처럼 숫자만은 아닌 번호도 그대로 동작합니다.
왜 이게 있어야 하나. 검색을 고쳐 402번을 찾을 수 있게 돼도, 노선도를 열면 정류장 목록이 캐시에 없어 빈 화면이 나옵니다. 그래서 처음 열 때 한 번만 받아와 채워 넣습니다.

이 함수 덕분에 사전 적재가 필수에서 최적화로 내려갔습니다. 배치를 한 번도 안 돌려도 앱은 정상 동작하고, 배치는 "자주 쓰는 노선을 미리 데워두는" 역할만 합니다. 이런 선택은 운영 부담을 크게 줄입니다 — 배치가 실패해도 서비스가 멈추지 않습니다.

07

수집 SDK가 지키는 약속

로그는 네트워크 단절이나 브라우저 종료 때문에 제때 도착하지 않을 수 있고, 그때 에러가 나지도 않습니다. 그래서 SDK는 "보냈다"가 아니라 "몇 건을 큐에 넣었고, 몇 건을 클라이언트에서 버렸는가"를 말할 수 있어야 합니다.

track은 전송하지 않는다

event_id를 클라이언트가 만듭니다. 전송이 실패해 재시도해도 같은 ID 가 유지되므로, 후속 적재 단계가 중복 제거 기준으로 쓸 수 있습니다. 서버에서 ID를 발급하면 같은 이벤트가 두 개가 됩니다.

다만 지금 확보한 것은 중복을 식별할 수 있는 키까지입니다. raw JSONL 수집 단계에서는 event_id 기반 서버측 dedup 을 하지 않으며, 중복 제거 자체는 후속 파이프라인의 책임입니다.

큐를 localStorage에 둡니다. 탭을 닫거나 오프라인이어도 남고, 다음 방문 때 전송됩니다. 부작용으로 지연 도착이 실제로 발생하는데, 이건 버그가 아니라 관측 대상입니다 — 서버가 queue_delay_ms(큐 대기)와 ingest_delay_ms(전송)로 나눠 기록합니다.

상한을 넘으면 오래된 것부터 버리고 센다. 최신 이벤트가 더 가치 있고, 무엇보다 dropped를 세어 다음 전송에 실어 보냅니다. 조용히 사라지면 서버는 유실이 있었다는 사실조차 모릅니다.

표시 실패가 수집을 막지 않게 리스너 호출을 try/catch로 감쌌습니다. 로그 패널 렌더링 오류 때문에 이벤트가 유실되면 본말이 뒤집힙니다.

이탈 시점 전송의 크기 제약

왜 이렇게까지 하나. beforeunload에서 fetch를 호출하면 브라우저 종료 과정에서 요청이 유지되지 않을 수 있습니다. 에러도 안 납니다. 이탈 시점 전송은 sendBeacon을 쓰고, beacon 본문 크기 제약을 고려해 50건 / 60,000바이트로 배치를 제한한 뒤 넘으면 앞에서부터 절반씩 줄여 나갑니다.

sendBeacon은 실제 서버 수신 결과를 돌려주지 않으므로 성공을 확정할 수 없습니다. 그래서 이벤트마다 seq를 함께 보존합니다. 지금 구현이 sequence gap 을 세지는 않지만, 후속 적재가 session_id + seq 로 유실 의심 구간을 찾아낼 수 있도록 재료를 남겨둔 것입니다.
전송 트리거 배치 10건 · 5초 경과는 fetch(keepalive)로, 탭 숨김과 페이지 이탈은 sendBeacon으로 보냅니다. 모바일에서는 앱 전환이 사실상 이탈이라 visibilitychange → hidden이 가장 신뢰할 수 있는 신호입니다. 그리고 doNotTrack이나 GPC가 켜져 있으면 수집 자체를 하지 않습니다.
08

수집 엔드포인트는 얇아야 한다

수집은 실패 확률을 최대한 낮추고, 한 건의 오류가 정상 이벤트까지 연쇄로 날려버리면 안 되는 경로입니다. 그래서 검증한 뒤 raw JSONL 에 붙이는 최소한의 일만 합니다 — 분석 DB에 쓰지 않고, 후속 파이프라인을 직접 호출하지 않습니다. 무거운 일은 전부 뒤로 미룹니다.

부분 수용. 50건 중 1건이 불량이라고 배치 전체를 400으로 돌려보내면, 클라이언트는 나머지 49건을 계속 재시도하다 결국 다 버립니다. 멀쩡한 이벤트가 불량 이웃 때문에 죽는 구조입니다. 받을 수 있는 건 받고, 못 받는 것만 사유와 함께 알립니다.

거부된 건 DLQ로. 클라이언트는 422를 받으면 그 데이터를 버립니다. 서버가 안 남기면 무엇이 왜 틀렸는지 영영 알 수 없습니다. 원문과 오류 목록을 함께 저장하고, 첫 오류에서 멈추지 않고 전부 모아 보냅니다 — 상류가 한 번에 고칠 수 있어야 하니까요.

IP는 수신 즉시 마스킹. 원본은 변수 밖으로 나가지 않습니다. 대역 단위 분석은 살리고 개별 식별은 막는 절충입니다.

지연은 거부 사유가 아니라 관측 대상. 기기 시각이 틀어져 있어도 이벤트를 버리지 않고, event_ts → sent_ts → ingest_ts 세 시각의 차이를 queue_delay_ms · ingest_delay_ms로 남깁니다. 시계 오차만 따로 재려면 별도의 시간 동기화 기준이 필요합니다.
지금의 신뢰·보안 경계 write_key는 브라우저에 그대로 실려 나가므로 비밀 인증키가 아닙니다. 지금은 등록된 클라이언트 설정을 식별해 서버가 service를 결정하는 용도일 뿐입니다. 공개 서비스라면 rate limiting, 남용 차단, 서명 같은 수단을 따로 둬야 합니다.

raw JSONL 단계에서는 event_id 기반 dedup 을 하지 않습니다. 클라이언트가 같은 event_id로 재시도할 수 있으므로, 후속 적재가 중복을 걸러낼 수 있도록 식별자를 보존해 둔 것입니다.
왜 시간 단위로 끊나. 적재 배치가 "아직 쓰이는 중인 파일"을 읽으면 마지막 줄이 잘려 있거나, 읽은 뒤에 추가된 이벤트를 놓칠 수 있습니다. 시간별 파일은 후속 적재에 "닫힌 시간대 파티션만 읽는다"는 단순한 경계를 줍니다.

다만 지금 구현은 파일이 닫혔다는 것을 명시적으로 표시하지 않습니다. 실제 운영에서는 안정화 지연을 두거나 manifest / commit marker 같은 경계 장치가 따로 필요합니다.
이 한 줄이 조용한 유실을 막는다 응답의 accepted와 rejected를 더하면 받은 이벤트 수와 정확히 같아야 합니다. 이 등식을 test_read_count_equals_accepted_plus_rejected가 검사합니다. 깨지면 어딘가에서 레코드가 사라진 것입니다.
09

화면 — 의도에서 시작하는 흐름

첫 화면이 검색창이 아니라 "무엇을 알고 싶으세요?"입니다. 같은 정류장 데이터라도 왜 왔는지에 따라 보여줄 것이 다르기 때문입니다.

세 번째 의도가 핵심입니다. catch_now는 what_comes와 같은 API 응답을 받고 soonOnly로 걸러내기만 합니다. 호출은 늘지 않는데 사용자가 얻는 답은 완전히 다릅니다 — "5분 안에 오는 버스가 없습니다"는 그 자체로 필요한 답입니다.

이벤트의 필드·열거값·검증 규칙·버전 이력은 docs/event-schema.md 한 곳에만 정의하고, 그 스키마를 왜 그렇게 정했는지는 docs/design-defense.html 에 반론과 함께 적었습니다 — 스키마가 README·설계 문서·코드 세 곳에 흩어지면 반드시 갈라집니다. 그리고 이 선택이 intent.select로 기록되고, 이후 모든 이벤트에 entry_intent(처음 고른 목적)와 current_intent(지금의 목적)가 함께 실립니다. 둘을 나눠 두면 "버스 위치를 보러 들어왔다가 정류장 도착정보로 넘어간 사용자"가 보입니다. 그래서 "급하다고 들어온 사람은 평균 몇 초 만에 떠나는가", "노선에서 출발한 세션과 정류장에서 출발한 세션의 행동이 어떻게 다른가" 같은 질문에 답할 수 있게 됩니다. 검색 로그만 있을 때는 없던 분석 축입니다.

화면은 데이터 출처를 모른다

app.js는 window.BusAPI라는 인터페이스만 압니다. 같은 인터페이스를 두 파일이 구현합니다.

구현데이터 출처쓰이는 곳
api-http.jsFastAPI 서버 (/api/...)실제 앱
api-mock.js브라우저 안 목업 데이터서버 없는 미리보기 · GitHub Pages

index.html에서 script 태그 한 줄만 바꾸면 전환됩니다. 덕분에 백엔드 없이도 화면 흐름 전체를 검증할 수 있었고, 미리보기 페이지를 따로 만들 필요가 없었습니다.

노선도를 좌표 없이 그리기

지도가 없습니다. API가 주는 건 위경도가 아니라 구간 순번(sectOrd)이라, 정류장 순서만 알면 그릴 수 있습니다. 덕분에 지도 SDK도, 지도 API 키도, 좌표 보간도 필요 없어졌습니다.

정차 중과 이동 중을 다르게 찍습니다. 정차 중이면 정류장 원 위에, 이동 중이면 gap/2만큼 밀어 두 정류장 사이에 놓습니다. API가 알려주는 건 "3번과 4번 사이"까지인데 이걸 "3번에 있음"으로 뭉뚱그리면 거짓말이 됩니다. 세로 목록에서도 채운 배지와 점선 배지로 같은 구분을 합니다.

색을 var(--bus-blue)로 씁니다. SVG 안에서 CSS 변수를 쓰면 다크 모드에서 자동으로 바뀝니다. 색을 하드코딩했다면 어두운 배경에서 안 보였을 겁니다.
두 층으로 나눈 이유 노선 하나에 정류장이 100개를 넘는 경우가 흔합니다. 한 화면에 다 넣으면 이름이 안 보이고, 세로 목록만 쓰면 버스가 어디쯤인지 감이 안 옵니다. 그래서 위에는 전체를 압축한 스트립, 아래에는 읽을 수 있는 세로 목록을 뒀습니다.
10

목업 모드를 만든 이유

키가 없으면 자동으로 목업으로 떨어집니다. 설정 실수로 조용히 빈 화면이 뜨는 대신, 시작 로그에 경고를 남기고 화면 상단에 "목업 모드" 배지를 띄웁니다.

목업을 만든 건 편의 때문만은 아닙니다. 세 가지가 따라옵니다.

대기 없는 실행

clone 한 사람이 인증키 발급을 기다리지 않고 바로 화면을 봅니다. 포트폴리오에서는 이게 큽니다 — 면접관이 5분 안에 돌려볼 수 있어야 합니다.

장애 구분

외부 API가 죽었을 때 무엇이 우리 코드 문제이고 무엇이 저쪽 문제인지 가릅니다. 목업으로 돌려서 정상이면 우리 쪽은 멀쩡합니다.

테스트 가능

테스트 전부가 목업 모드로 돕니다. 외부 호출 없이, 인증키 없이, CI에서도 그대로 실행됩니다(.github/workflows/ci.yml). 처음 25개였던 회귀 범위를 코드 리뷰와 실데이터 연동을 거치며 109개까지 늘렸습니다. 브라우저 SDK 는 프레임워크 없이 node tests/collector_selfcheck.js 자체 점검 하나로 봉투 규약을 고정합니다.

목업이 일부러 불완전한 이유 mock.ROUTES에는 버스가 4개인데 시작 시 캐시에 넣는 SEEDED는 3개뿐입니다. 나머지 402는 "캐시에 없는 버스"를 연기합니다. 덕분에 06장의 실시간 폴백 경로가 목업 모드에서도 실제로 실행되고, 로그 패널의 endpoint 값이 cache:routes에서 노선번호목록조회로 바뀌는 것을 눈으로 확인할 수 있습니다.
11

요청 하나를 끝까지 따라가기

"버스가 어디쯤인지 보고 싶다"를 고르고 402를 검색해 노선도를 여는 동안 무슨 일이 일어나는지입니다. 402는 사전 적재하지 않은 버스입니다.

  1. 의도 선택

    첫 화면에서 카드를 누릅니다. 아직 아무 API도 부르지 않습니다.

    → intent.select { next_mode: route, entry_intent: where_bus, current_intent: where_bus }

  2. 검색어 입력

    app.js가 BusAPI.searchRoutes("402")을 호출합니다. 화면은 이게 캐시인지 외부인지 모릅니다.

  3. 캐시 확인 — 미스

    store.search_routes가 빈 리스트를 돌려줍니다. 정확히 일치하는 번호가 없으므로 실시간 경로로 내려갑니다.

  4. 외부 조회

    노선번호목록조회를 부르고, XML을 파싱해 headerCd를 확인하고, normalize("route", ...)로 모양을 맞춥니다.

    → api.call { endpoint: 노선번호목록조회, latency_ms: 214, cache: miss } · event_type=system

  5. 캐시에 채움

    store.upsert_routes(found). 이 순간부터 402는 캐시에 있습니다. 다음 검색은 호출 0회입니다.

    → search.query { search_id: sq-3f9a, search_type: route, query: 402, result_count: 1, result_status: success, data_source: live }

  6. 결과 클릭

    순위 정보가 함께 기록됩니다. 몇 번째를 눌렀는지가 검색 품질 지표의 재료입니다.

    → search.click { search_id: sq-3f9a, position: 1, route_id: 233000112 }

  7. 정류장 목록 확보

    _ensure_stations가 캐시 미스를 확인하고 노선별경유정류소목록조회를 한 번 부른 뒤 저장합니다. 이 노선의 정류장 목록은 이제 영구히 캐시에 있습니다.

  8. 버스 위치 조회

    _live가 TTL 캐시를 보고 미스라 외부를 부릅니다. 20초 안에 다시 열면 이 호출은 생략됩니다.

    → api.call { endpoint: bus_pos, latency_ms: 188, cache: miss, data_age_sec: 0 }

  9. 렌더링

    정류장 순번 위에 버스를 얹고, 정차/이동을 구분해 그리고, 우측 상단에 "0초 전"을 표시합니다.

    → route.view { route_id: 233000112, stop_count: 11, running_bus_count: 2, search_id: sq-3f9a }

  10. 전송

    이벤트 5개가 쌓이면 collector.js가 배치로 POST /v1/collect에 보냅니다. 서버가 검증해 events-2026-09-16-14.jsonl에 붙입니다.

두 번째 사용자부터 사전 캐시가 채워져 있다면 같은 흐름에서 외부 호출이 3회 → 1회로 줍니다. 노선 검색과 정류장 목록은 캐시에서 나오고, 버스 위치는 20초 TTL 의 준실시간 데이터로 다룹니다. 20초 안에 같은 조회가 반복되면 그 호출도 캐시에서 처리됩니다.

코드 리뷰에서 나온 것

동작하는 코드와 운영을 고려한 코드는 다릅니다. 시니어 관점으로 한 번 더 읽으면서 추측이 아니라 재현으로 문제를 확인하고 고쳤습니다.

발견무엇이 문제인가어떻게 확인했나
연결 누수sqlite3.Connection 의 with 는 트랜잭션만 관리하고 연결을 닫지 않는다. 쿼리마다 연결이 열리고 GC 에 맡겨졌다with 블록 뒤 execute 성공

신뢰 경계 위반설계서에는 "본문의 service 를 믿지 말고 write_key 로 도출하라"고 써놓고 코드는 본문 값을 그대로 저장하고 있었다grep
신선도가 거짓data_tm 을 파싱해 놓고 쓰지 않았다. 화면의 "N초 전"은 캐시 나이였다 — 90초 묵은 데이터가 "0초 전"으로 표시됐다필드 사용처 추적
캐시 만료 실패int(now - stored) 로 잘라 비교해 TTL 을 막 넘긴 값이 그대로 나갔고, 만료 항목이 지워지지 않아 메모리가 계속 늘었다TTL 1초 재현
무제한 수집/v1/collect 에 본문 크기·건수 상한이 없었다코드 확인
죽은 인덱스stations.name 인덱스를 LIKE '%q%' 가 쓸 수 없다. 쓰기 비용만 늘리고 있었다EXPLAIN QUERY PLAN
측정 없는 한도설계 전체가 하루 1,000회 위에 서 있는데 실제 사용량을 세는 곳이 없었다—

① 연결을 스레드마다 하나만

무엇이 문제였나. with connect() as conn: 을 쿼리마다 썼습니다. 파이썬에서 이 구문은 커밋/롤백만 하고 close() 는 하지 않습니다. CPython 의 참조 카운팅이 뒤늦게 수거해줘서 터지지는 않지만, 요청마다 연결을 새로 여는 비용은 그대로 들고 WAL 파일 핸들도 함께 열립니다.

FastAPI 가 동기 작업을 제한된 스레드풀에서 돌리므로 스레드 수가 유한합니다. 그래서 스레드 로컬로 하나씩 재사용하는 게 가장 단순하면서 새지 않는 방법입니다. 쓰기는 tx() 로 감싸 커밋과 롤백을 보장했습니다.

② 만료를 제대로 판정하고, 메모리에 상한을 둔다

두 가지가 겹쳐 있었습니다. 나이를 int() 로 잘라 비교해서 TTL 20초일 때 20.9초 지난 값이 age=20 으로 계산돼 만료로 걸리지 않았고, 만료된 항목을 돌려주지 않을 뿐 지우지도 않아 조회된 모든 키가 영원히 남았습니다.

이제 float 로 비교해 즉시 지우고, OrderedDict 로 LRU 상한을 둡니다. 덤으로 히트율을 세어 /api/health 에 노출했습니다 — 캐시는 효과를 측정하지 않으면 그냥 복잡도입니다.

③ 설계서가 맞고 코드가 틀렸던 부분

가장 뼈아픈 발견입니다. 설계서에는 "클라이언트가 보낸 service 를 믿으면 안 된다"고 적어 놓고, 코드는 batch.get("service", ...) 로 본문 값을 그대로 저장하고 있었습니다. 문서와 구현이 갈라져 있었던 셈입니다.

지금은 write_key 로만 도출하고, 등록되지 않은 키는 401 로 거부합니다. 문서에 적은 원칙은 테스트로 고정해야 지켜집니다 — test_service_comes_from_write_key_not_body 가 그 역할을 합니다.

④ 사용자에게 보여주는 신선도는 우리 캐시 사정이 아니다

이 프로젝트가 자랑하던 것이 거짓이었습니다. 화면 우측의 "N초 전"은 데이터 나이가 아니라 캐시에 들어온 지였습니다. API 응답의 dataTm 을 파싱해 놓고 아무 데도 쓰지 않았던 겁니다. 앞선 프로젝트에서 ingest_ts 와 sent_ts 를 구분했던 것과 정확히 같은 실수를 반복했습니다.

고치고 나니 또 다른 버그가 드러났습니다. 목업이 datetime.now() 로 시각을 찍는데 컨테이너가 UTC 라, 신선도가 32400초(정확히 9시간)로 나왔습니다. 타임존을 붙이지 않은 대가입니다. 목업도 KST 로 고치고 회귀 테스트를 붙였습니다.

⑤ 관리하려면 먼저 측정한다

계층을 지키면서 알리는 방법. seoul_api.py 는 DB 를 몰라야 하므로 직접 기록하지 않고 콜백만 호출합니다. main.py 가 client.on_call = store.record_api_call 로 연결합니다. 기록이 실패해도 조회는 계속되도록 try/except 로 감쌌습니다 — 부가 기능이 본 기능을 죽이면 안 됩니다.
KST 기준으로 세는 이유. 한도는 한국 시간 자정에 초기화됩니다. UTC 로 집계하면 오전 9시에 날짜가 바뀌어 "오늘 몇 회 썼나"가 틀립니다. 실패한 호출도 한도를 소모하므로 함께 셉니다. 결과는 /api/health 의 api_usage 로 나옵니다 — 남은 횟수와 엔드포인트별 사용량까지. 다만 이건 관측 지표이지, 1,000회를 넘기 전에 호출을 막는 quota gate 는 아닙니다.

⑥ 수집 엔드포인트에 상한을 둔다

세 가지를 한꺼번에. 본문을 파싱하기 전에 크기를 보고(Content-Length 를 속일 수 있으니 실제 바이트도 다시 확인), 이벤트 건수에 상한을 두고, 파일 쓰기는 스레드풀로 넘겨 이벤트 루프를 막지 않게 했습니다. 수집 경로가 동기 파일 I/O 로 이벤트 루프를 붙잡지 않게 하는 것이 핵심입니다. 물론 이것으로 파일 시스템 자체의 장애가 사라지지는 않으므로, 실제 운영에서는 별도 큐·스토리지와 디스크 모니터링이 필요합니다.

실데이터 연동 — 목업이 절대 못 잡는 것들

여기까지는 전부 목업 모드로 통과한 코드입니다. 그런데 목업이 증명하는 것은 "내 코드가 내 가정대로 동작한다"까지입니다. 그 가정이 실제 응답과 맞는지는 명세를 대조해야 압니다. 공공데이터포털 항목표를 하나씩 맞춰보니 여러 곳이 어긋나 있었습니다.

여기서 한 번 틀렸습니다 처음에는 다른 오퍼레이션(getArrInfoByRouteAll)의 항목표를 보고 reride_Num1 을 혼잡도 코드로 읽었습니다. 정류소도착정보의 정식 명세를 받아보니 필드명은 rerideNum1(밑줄 없음)이고 뜻은 재차인원(명)이었습니다. 이름과 의미가 둘 다 틀렸던 겁니다.

배운 것: "비슷한 API 니까 같겠지"가 가장 위험합니다. 같은 기관, 같은 도메인의 형제 오퍼레이션인데도 stationNm/stNm, station/stId 처럼 필드 규칙이 다릅니다. 오퍼레이션마다 명세를 따로 봐야 합니다.
어긋난 것왜 위험한가목업이 못 잡는 이유
congetionAPI 명세의 철자가 오타난 채로 확정돼 있습니다. 정상 철자 congestion 으로 읽으면 혼잡도가 전부 "정보없음"이 됩니다목업은 내가 정한 이름으로 값을 넣으므로 늘 맞는다

상·하행 — API 가 안 주는 것을 만들어 내기

한계 항목에 "상행/하행 분리 — 토글이 비활성"이라고 적어뒀던 것을 이번에 구현했습니다. 명세를 보니 이 API 는 방향을 따로 주지 않습니다. 기점에서 종점까지 seq 가 1..N 으로 한 줄로 내려오고, 그 안의 회차지(transYn='Y')가 방향이 바뀌는 지점입니다.

없는 방향을 지어내지 않습니다. 회차지 표시가 없는 노선(편도·순환)은 토글을 감추고 "편도 · 회차 구간 없음"이라고 적습니다. 데이터가 없는데 UI 를 채우면 사용자가 있지도 않은 방향을 고르게 됩니다.

방향 전환은 외부 호출 0회입니다. 이미 받아둔 같은 응답을 다시 그릴 뿐입니다 — 09장의 catch_now 필터와 같은 원리이고, 회귀 테스트가 이 토글 코드에 BusAPI. 호출이 없는지까지 확인합니다.

목업도 왕복으로 바꿨습니다. 목업이 편도만 주면 방향 분리 코드가 목업 모드에서 한 번도 실행되지 않습니다. 데모에서는 멀쩡하다가 실데이터에서 처음 터지는 코드가 되는 겁니다 — 목업의 값은 가짜여도 모양은 진짜와 같아야 하는 이유입니다.
그래도 남는 것 위 셋은 명세를 읽어서 고친 것이지 실호출로 확인한 것이 아닙니다. 그래서 scripts/smoke_live.py 를 따로 뒀습니다 — 엔드포인트마다 1회씩(총 5~6회, 하루 한도의 0.6%) 부르고 정규화 전 원본 필드명과 정규화 후 값을 나란히 찍습니다. 필드명이 어긋나면 정규화 값이 빈 문자열로 떨어지는데, 그게 바로 눈에 보이게 만든 것입니다.
리뷰에서 배운 것 위 항목 중 절반 가까이가 "문서에는 맞게 써놓고 코드는 다르게 한" 종류였습니다. 신뢰 경계, 신선도 기준, 인덱스 효과 — 전부 문서에 원칙을 적어둔 항목입니다. 글로 적은 원칙은 지켜지지 않고, 테스트로 고정한 원칙만 지켜집니다. 그래서 이번 수정은 전부 회귀 테스트와 함께 들어갔습니다(25개 → 109개).
